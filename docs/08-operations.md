# 08. 開発・運用

## 8.1 セットアップ

```bash
npm install
npm run dev      # http://localhost:3000
```

初回起動時に `data/monote.db` が自動作成され、デモデータがシードされる（→ [07](./07-seed-data.md)）。

本番ビルド:

```bash
npm run build && npm start   # ポート3000
```

DBの作り直し:

```bash
rm -f data/monote.db*
npm run dev
```

### npm スクリプト

| スクリプト | 内容 |
|---|---|
| `dev` | `next dev -p 3000` |
| `build` | `next build` |
| `start` | `next start -p 3000` |
| `seed` | `node --experimental-strip-types lib/seed-cli.ts` — ⚠️ **`lib/seed-cli.ts` が存在しないため現状は失敗する**。シードは `lib/db.ts` の初回起動時実行が本流 |

### 主要な依存

| パッケージ | バージョン |
|---|---|
| `next` | `^16.3.3` |
| `react` / `react-dom` | `^19.2.8` |
| `better-sqlite3` | `^13.0.3` |
| `typescript` | `^7.0.2`（devDependency） |

TypeScript は `strict: true`、`moduleResolution: "bundler"`、パスエイリアス `@/*` → リポジトリルート。
リンタ・テストランナーは未導入。

## 8.2 エージェント向けの規約

リポジトリ直下に `AGENTS.md`（`CLAUDE.md` が `@AGENTS.md` で読み込む）がある。

> **This is NOT the Next.js you know**
> このバージョンには破壊的変更があり、API・慣習・ファイル構成が学習データと異なる可能性がある。
> コードを書く前に `node_modules/next/dist/docs/` の該当ガイドを読むこと。
>
> このブロックは `next dev` が書き込み・再追加するもの（`node_modules/next/dist/server/lib/generate-agent-files.js`）。
> 差分から消しても再生成されるだけなので、作業と一緒にコミットしてツリーをきれいに保つこと。

コード側の規約:
- `lib/repo.ts` は **ページ実装から見て READ-ONLY**。追加クエリは `lib/extra/<page>.ts` に置く
- 書き込みは Server Actions 経由（REST API ルートは持たない）
- CSS は画面ごとのファイルに分け、トークンは `css/base.css` に集約

## 8.3 デプロイ

### Vercel（デモ用途）

そのままデプロイできる。ただしサーバーレス環境ではファイルシステムが読み取り専用のため、
`lib/db.ts` が SQLite を `/tmp` に作成・シードする。

その結果:
- **書き込み（保存・比較・相談・記事公開など）はインスタンスローカルかつ一時的**
- コールドスタートでシード状態に戻る
- 複数インスタンスに分かれると、書き込みが他のインスタンスから見えないことがある

デモとして触ってもらう分には成立するが、**評価用の共有環境としては注意が必要**。

### 永続化する場合

| 選択肢 | 内容 |
|---|---|
| 永続ディスクのあるホスティング | Render / Railway / Fly.io / VPS などで `npm run build && npm start` |
| DBの差し替え | `lib/db.ts` の接続を **Turso(libSQL)** や **Postgres** に置き換える |

DBアクセスは `lib/repo.ts` と `lib/extra/*` に集約されているため、
差し替えの影響範囲は限定的（ただし `better-sqlite3` の**同期API**前提のコードを
非同期に書き換える必要はある）。

## 8.4 既知の制約

| # | 制約 | 影響 | 対応の方向 |
|---|---|---|---|
| 1 | **認証がデモ実装** — パスワード検証なし、Cookie の値がそのままユーザーID | 本番不可 | 署名付きセッション / IdP 連携へ差し替え |
| 2 | **Server Action の権限チェックが場所によりまちまち** — `/admin` 系は `currentUser()` で検証するが、保存・比較・相談はセッションキーのみ | なりすまし相談の余地 | アクション側での一貫した認可 |
| 3 | 相談の添付は**ファイル名の文字列だけ**を保存（実体のアップロードなし） | 図面が送れない | ストレージ連携 |
| 4 | 相談の通知（メール等）が無い | 受信箱を見に行かないと気づけない | 通知基盤 |
| 5 | `npm run seed` が参照する `lib/seed-cli.ts` が存在しない | スクリプトが失敗する | ファイル追加、またはスクリプト削除 |
| 6 | README の「Next.js 15」表記が `package.json`（`^16.3.3`）と食い違う | 誤解のもと | README 更新 |
| 7 | SQLite 同期APIのため、水平スケール不可 | 本運用に不向き | 8.3 のDB差し替え |
| 8 | 記事の審査・通報フローが未実装（`reviewed` フラグのみ） | 構想の「品質・信頼性」対策が未達 | 審査キュー・通報導線 |
| 9 | 画像容量・投稿上限の制御が無い | 構想が挙げる「原価圧迫」リスクが未対策 | 上限設計 |
| 10 | 課金導線が存在しない | 有料意向を測れない（＝停止条件の判断材料が欠ける） | 資料請求・見積導線の設置 |
| 11 | 緩和サジェストは `delivery` カテゴリ限定 | 他条件で0件のとき行き止まり | 一般化 |
| 12 | テスト・リンタが未導入 | 回帰検知ができない | 最低限の型チェック＋E2E |

## 8.5 構想 → 実装のギャップ（次の一手）

構想資料の主張と、現在の実装の対応関係。

| 構想の要素 | 実装状況 |
|---|---|
| 製造業の条件で探せる | ✅ 7カテゴリ27条件で成立 |
| 記事と企業情報を一体で確認 | ✅ 記事⇄企業⇄検索が相互接続 |
| 保存・比較・相談へ接続 | ✅ 一気通貫で動作 |
| 反応・相談行動の可視化 | ✅ `/admin` ダッシュボード |
| 編集品質による信頼 | ⚠️ `verified` / `reviewed` の表示のみ。運用フローなし |
| 検索軸「業種・用途」「設備・能力」「課題・目的」 | ⚠️ テキスト止まり。**条件化の候補** |
| 優先表示・レコメンド（有料） | ❌ ランキング関数に枠を差せる構造はあるが未実装 |
| 運用代行（有料） | ❌ 導線なし |
| ターゲット配信・再掲 | ❌ 未実装 |
| 通報・審査 | ❌ 未実装 |
| 画像容量・投稿上限 | ❌ 未実装 |

### 優先度の提案

1. **検証を先に進めるもの**（構想の停止条件を判断するために必要）
   - 有料プランへの関心を測る導線（資料請求・問い合わせ）
   - 企業別の継続投稿率が見える画面
   - 緩和サジェストの採用率の計測
2. **信頼性の土台**（オープン化の前提）
   - 認証の差し替え（#1, #2）
   - 記事の審査・通報フロー（#8）
   - 投稿上限・容量制御（#9）
3. **検索の深化**
   - 「業種・用途」「設備・能力」「課題・目的」の条件化
   - 緩和サジェストの全カテゴリ対応
